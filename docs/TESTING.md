# Testing strategy

Vitest is installed for focused server-side behavior tests.

TASK-002 provides a database smoke script that opens a real adapter-backed connection and performs safe count queries against core seed tables. Schema validation, migration status, idempotent seeding, and this smoke check form the database-foundation verification set. They require a running PostgreSQL instance.

TASK-003 tests credential validation and normalization, real bcrypt hashing and verification, active and inactive users, invalid passwords, limiter denial and fail-closed behavior, generic public errors, and ADMIN/STAFF role enforcement. `npm run test:auth:integration` verifies provisioning, valid and invalid credentials, protected access, inactive-user revocation, STAFF shell access, and sign-out against PostgreSQL and a running application. It leaves its fixed verification account inactive and never prints the generated password.

TASK-004 tests product visibility, category filtering, invalid lookups, variant availability, exact and variable price labels, primary-image selection, fallback images, and safe public DTO shaping. `npm run test:catalogue:integration` checks the seeded catalogue against PostgreSQL, including category/product counts, hidden fixtures, variants, image metadata, and unavailable stock examples.

TASK-005 tests centralized purchasability and command validation, including inactive variants, inactive or unpublished products, zero stock, fractional and out-of-range quantities, malformed identifiers, and incomplete references. `npm run test:inventory:integration` uses temporary PostgreSQL fixtures to verify increases, decreases, exact-stock consumption, insufficient-stock failure, audit accuracy, rollback behavior, the database non-negative constraint, and a real concurrent one-unit race. The script removes only its uniquely named verification records.

TASK-006 tests persisted cart validation and recovery, unsupported versions, invalid quantities, duplicate merging, line and total limits, cart mutation limits, total-unit counts, and in-session price-change detection. `npm run test:cart:integration` uses temporary PostgreSQL fixtures to verify authoritative multi-line totals, ignored client prices, hidden and inactive products, inactive and zero-stock variants, stale quantity adjustment, refreshed prices, and safe DTO shaping.

TASK-007 tests guest-detail normalization, invalid email, missing address fields, U.S.-only country and ZIP validation, field-length bounds, standard and free shipping, zero-tax behavior, and integer-cent totals. `npm run test:checkout:integration` uses temporary PostgreSQL fixtures to verify current pricing, ignored fake totals, standard and free shipping, hidden products, inactive and zero-stock variants, insufficient-stock rejection, safe DTO shaping, and zero changes to order, payment, stock, and inventory-movement records.

TASK-008 unit tests cover payment request validation, ignored client totals, order numbers, HMAC/fingerprint behavior, server-derived Stripe line items, raw webhook signature rejection, customer payment-state mapping, and verified-only cart clearing. `npm run test:payment:integration` uses temporary PostgreSQL fixtures and a fake Stripe network adapter to verify order/payment snapshots, failed Session creation, attempt idempotency, event-level and payment-level idempotency, duplicate and concurrent delivery, test/live isolation, amount/currency mismatch, unknown sessions, safe stock exhaustion, audit records, and transaction rollback. It removes only its uniquely identified fixtures.

End-to-end Stripe-hosted and CLI-forwarded webhook QA requires valid local test credentials and a listener-provided webhook secret. It is not considered complete until that environment is configured.

`npm run payment:diagnose -- --remote` is a read-only, redacted comparison of recent PostgreSQL payment state, webhook outcomes, and Stripe sandbox Session/event state. If a real test-mode completion event was missed while the local listener was offline, `npm run payment:reconcile:sandbox -- --order=MV-...` performs a dry run. Adding `--apply` is allowed only outside production after test mode, paid/complete state, event existence, internal linkage, amount, and currency all match. It reuses the normal idempotent webhook processor with a deterministic reconciliation ledger id.

TASK-009 unit tests cover reference/email normalization, constant-time HMAC proof helpers, signed-session tamper and expiry rejection, payment and fulfillment status mapping, destination masking, and sensitive-field exclusion. `npm run test:orders:integration` uses temporary PostgreSQL orders to verify valid lookup, generic missing/wrong-proof behavior, cross-order isolation, expiration, operational review mapping, masked allow-listed DTOs, and real database-backed rate-limit enforcement. Fixtures and their exact HMAC buckets are removed afterward.

TASK-010 unit tests cover slug normalization, curated-image allow-list enforcement, price relationships, bounded category input, ADMIN mutation authority, and STAFF read-only policy. `npm run test:admin-catalogue:integration` uses uniquely named PostgreSQL fixtures to verify transactional product and initial-variant creation, duplicate SKU rollback, product editing and storefront visibility, variant editing and archival, category safety, audited inventory setting, and stale-write rejection. It removes only its own movements, products, variants, and categories.

Storefront stock UX tests cover the greater-than-ten, one-through-ten, zero, and unavailable thresholds; initial and switched variant state; sold-out add prevention; concise add-to-bag confirmation; and repeated cart additions. Existing catalogue, cart, checkout, inventory, payment, and order tests continue to verify that browser messaging does not replace authoritative server checks.

TASK-011 unit tests cover bounded order search/filter input, role permissions, status labels, sequential transition policy, skipped and unsupported transition rejection, unpaid protection, inventory/payment-review locks, and manual action mapping. `npm run test:admin-orders:integration` uses temporary PostgreSQL fixtures to verify reference and email search, filters, paid dispatch and delivery, actor history, exact one-event behavior under concurrent duplicate submissions, invalid-transition rollback, and unchanged payments, financial totals, item snapshots, stock, and movement history. It removes only its uniquely named order and catalogue fixtures.

TASK-012 unit tests cover period validation, inclusive UTC boundaries, refund/net/average calculations, pending and failed payment exclusion, duplicate payment-row protection in chart shaping, stock thresholds, and empty trends. `npm run test:admin-analytics:integration` uses isolated future-dated PostgreSQL fixtures to verify captured-status gross sales, persisted refunds, net sales, distinct paid orders, date filtering, payment/inventory exceptions, immutable snapshot rankings, current stock alerts, duplicate webhook-ledger isolation, and exclusion of customer and provider identifiers. The script removes only its uniquely named fixtures.

TASK-013 extends catalogue tests with colour-specific gallery selection, primary-image selection, legacy fallback behavior, curated allow-list rejection, and continued sensitive-field exclusion. `npm run test:catalogue:integration` additionally requires at least two optimized local WebP photographs for every public seeded product. Manual QA should cover 320 px, 768 px, 1024 px, and wide layouts; keyboard-only gallery, variant, cart, checkout, lookup, and admin paths; 200% zoom; reduced motion; visible focus; image alternatives; and basic screen-reader announcements. Automated checks do not replace browser accessibility and visual review.

TASK-014 unit tests cover trusted proxy parsing, spoofed forwarding-header refusal, canonical production origins, byte-accurate request limits, production PostgreSQL TLS requirements, operational command gates, production environment validation, and source-wide rate ceilings. CI starts PostgreSQL 17, installs from the lockfile, generates Prisma, deploys migrations, seeds only the isolated CI database, then runs lint, typecheck, unit tests, PostgreSQL integration suites, and the production build.

Security verification also includes `npm audit`, `npm audit --omit=dev`, `npm outdated`, Prisma validation/status, a tracked-file secret-pattern scan, and `git diff --check`. Audit severity is reported with dependency path and runtime applicability; force-fixing through incompatible major downgrades is not accepted. Hosted security-header, cookie, proxy, webhook, and browser QA remains part of TASK-015 because local automation cannot prove platform behavior.

TASK-015 adds metadata-route tests, production pool configuration coverage, a local 25-asset manifest/file-format check, and a read-only hosted smoke script. `npm run deployment:assets` verifies 24 product photographs plus the editorial image. `npm run qa:hosted -- --url=https://HOST` checks public routes, sitemap and robots boundaries, security headers, all optimized images, unauthenticated admin redirect behavior, and missing-Origin rejection. It intentionally cannot prove authenticated roles, cookies, Stripe Checkout, webhook delivery, database outcomes, logs, accessibility, backups, or responsive presentation; those remain manual hosted evidence.
